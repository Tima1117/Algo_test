## Как всё устроено (то, что спросят на созвоне)

- `python -m pif all` — одна команда: реестр → сбор → нормализация → притоки → сверка → отчёт качества.
  `make all` — то же плюс сборка сайта.
- **Реестр** (`pif/registry.py`): xlsx Банка России «Сведения о ПИФ» → фильтр «открытый/интервальный/биржевой»,
  статус «сформирован/формируется», не для квалов → 395 фондов у 52 УК. ИНН УК — из реестра лицензий УК ЦБ
  (склейка по ОГРН, в реестре фондов ИНН нет). ISIN/тикер — ISS Мосбиржи (склейка по номеру правил).
- **HTTP-клиент** (`pif/http.py`): 1 запрос/с на домен, честный User-Agent, каждый ответ сохраняется в `raw/`
  (в git не лежит), в `data/manifest.json` — адрес, дата, формат, SHA-256, какие фонды. Повторный запуск
  в течение 20 часов в сеть не ходит; позже — условный запрос (ETag/Last-Modified). Капча/403 — статус
  «закрыт доступ», не обходим. Сайт упал — берём последнюю сохранённую копию и помечаем «не обновилось».
- **Адаптеры УК** (`pif/sources/<ук>.py`): по одному на управляющую компанию, подхватываются автоматически.
  Разбор — отдельные чистые функции, на незнакомых данных бросают `UnknownFormat` (никаких тихих нулей).
  Тесты — на настоящих ответах сайтов в `tests/fixtures/<ук>/`.
- **Нормализация** (`pif/normalize.py`): слияние выгрузок по дате (свежая побеждает), выбросы, дробление паёв
  (цена прыгнула в 10/100/1000 раз, а СЧА — нет), СЧА в тысячах вместо рублей. Каждое исправление — в журнал.
  Пропуски не заполняются.
- **Притоки** (`pif/flows.py`): `приток = СЧА_м − СЧА_{м−1} × пай_м / пай_{м−1}` по последней точке месяца.
  Логика: если бы паёв не выдавали и не гасили, СЧА изменилась бы ровно как пай. Всё сверх — деньги пайщиков.
  Нет точки за прошлый месяц — приток не считается (пропуск, не ноль). Валютные фонды — в рубли по курсу ЦБ.
  Тест с заранее известными числами: `tests/test_flows.py`.
- **Сверка доходности** (`pif/returns.py`): доходность пая за 1/3/6/12 мес по нашему ряду vs официальная
  с сайта УК на ту же дату; > 0,5 п. п. — в отчёт и значок ≠ на сайте.
- **Публикация**: `--strict` возвращает ошибку, если в отчёте есть ошибки сбора/разбора; тогда CI не коммитит
  данные и Vercel не деплоит. Расхождения доходности публикацию не блокируют.
- **Сайт** (`site/`, Astro): статическая сборка, base path `/pif/` (меняется переменной `PIF_BASE`), страницы
  `/pif/fund/<номер правил>/`, `/pif/uk/<ИНН>/` готовым HTML, фильтры и сортировка в адресной строке,
  графики — uPlot (MIT), шрифты локально (@fontsource, OFL). Ничего внешнего не грузится.

## Решения, которые стоит уметь объяснить

- **Почему 395, а не 559 фондов.** В заголовке задания «розничные». 164 действующих фонда — только для
  квалифицированных инвесторов, их отбросили и написали об этом на сайте.
- **Почему не все УК собраны.** Часть сайтов недоступна из сети, где работает сборщик (ВИМ, Атон, БКС, РСХБ,
  ААА, Ак Барс и др. — 403 или таймаут из-за рубежа). Это показано статусом с причиной. С российского IP
  они, скорее всего, откроются — это первое, что делать дальше.
- **Почему данные лежат в git.** Сайт — чистая статика, Vercel собирает его из `data/site` и `data/series`.
  Сырые файлы (xlsx/json/html с сайтов) в git не лежат — только манифест с SHA-256.
- **Почему CI по расписанию может не видеть часть УК.** GitHub Actions работают с зарубежных IP. Честное
  решение — self-hosted runner на российском сервере; пока описано как ограничение.

## Известные проблемы и что нашли сами

- Фонды с выплатой дохода (например, «СОЛИД – Денежный поток»): доходность по цене пая без учёта выплат
  расходится с официальной (УК считает с выплатами). Это реальная особенность, а не ошибка сбора — расхождение
  показано на сайте.
- Ссылка «Сравнить УК» ведёт на https://algosphere.tech/sravnenie/?inn=… — сам раздел пока не умеет
  открываться на конкретной УК (это SPA без параметров). Описать в README как точку интеграции.
